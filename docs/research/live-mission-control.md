# Live Agent Mission Control: repository comparison and integration approach

Date: 2026-11-11. Status: first deliverable (research and proposals), no change to the running architecture yet.
Scope: extend Second Brain Business OS with a real-time multi-agent monitoring and management surface (fleet overview, live agent map, run inspector, management control). Method: the four repositories were cloned shallowly into an isolated directory and read; nothing from them was executed or installed. Every claim below cites a file in the repository.

Reading: every candidate is a full product with its own orchestrator or its own ingestion path. None was built as a library for someone else's runtime, none has PostgreSQL row-level security, and all four fan events out from a single process. Adopting one as a service would mean running a second orchestrator beside pg-boss and Mastra; embedding one's UI would mean importing its API client, its router and its store. Both conflict with ADR-012 (agents run only in our worker) and with the tenant isolation rule (RLS in PostgreSQL, `withContext()` everywhere).

## 3. Recommended integration approach (safest)

Principle: our database already is the event bus. The worker writes every state change, step, tool call, model call, approval and checkpoint to `run_events` (append-only, RLS per tenant); Mission Control reads it through the operator role. Nothing from the four repositories replaces that. We add one transport, one table column, one package of UI components, and no second orchestrator.

1. **Transport: SSE from a Next.js route handler, fed by PostgreSQL LISTEN/NOTIFY.** A trigger on `run_events`, `approvals`, `incidents`, `sync_runs` and `agent_instances` raises `NOTIFY sbos_live, '{"tenantId":..,"kind":..,"id":..}'` (identifiers only, no content). The route `GET /api/mission-control/stream` authenticates with Better Auth (operator role with MFA, same `requireOperatorContext()` gate), holds one dedicated `pg` client for LISTEN (not the pooled RLS connection), and on each notification re-reads the row through `withContext()` with the operator context, so RLS and the column grants decide what the stream may carry. Snapshot first (`?since=<last event id>`), then stream; heartbeat every 30 s; the client hook (mission-control pattern) reconnects with backoff and polls when disconnected. This works across several web replicas because the fan-out is in PostgreSQL, and it works without any developer session (ADR-012). WebSockets are not needed: the stream is server to client only; commands go through existing server actions.
2. **Data model additions (one migration).** `runs.parent_run_id` (delegation and sub-agents, from the mission-control and paperclip models), `run_instructions` (text, actor, created_at, consumed_at, checkpoint step; consumed by the executor at the next `saveCheckpoint`, which is the only safe injection point in the checkpointed flow), and a documented JSON payload per `run_event_kind` (paperclip's TranscriptEntry as the template: tool name, target, duration, result summary, tokens, cost, never raw prompts or content). `run_events` already carries durations and costs through `cost_events`.
3. **UI: a `mission-control-live` component set in `apps/web/components/live/`.** React Flow 12 plus dagre (pinned) for the map, copied from conductor with the license notice and restyled with our tokens (navy `--sb-bg`, cyan `--sb-cyan`, indigo `--sb-indigo`); fleet cards and widget grid after the mission-control widget layout; inspector panels after conductor's activity stream; gate and guidance dialogs after conductor's. Icons: our existing text badges, no icon library (consistent with the current shell).
4. **Controls reuse what exists.** Pause, resume, stop, run now, approve and reject already exist as audited server actions in Mission Control; "answer question" exists in the client workspace; "instruct at checkpoint" and "reassign task" are new actions over the new table and the existing `tasks.agent_instance_id`. Agents never get a control path (migration 0010 restrictive policies stay).
5. **What we explicitly do not do.** No embedding of any of the four UIs; no second orchestrator; no WebSocket server; no event payloads with vault content; no bypass of RLS for the stream.

Risks and mitigations: a NOTIFY payload is limited to 8000 bytes (we send identifiers only); a long-lived LISTEN connection per web replica (one, shared by all stream clients of that replica); RLS re-read per notification costs one query per event (acceptable at our volumes; batch when more than 20 events per second). Fallback: if SSE is blocked by a proxy, the client hook polls `GET /api/mission-control/snapshot` every 5 s with the same filters.

## 4. The three visual proposals

Each proposal is a separate, interactive prototype on the same synthetic simulation (`docs/proposals/live-mission-control/sim.js`: 3 synthetic clients, 21 agent instances, real `run_state`, `run_event_kind`, `task_state`, `approval_state` and `incident_kind` vocabularies, pg-boss queue names, scripted failures, waits, approvals and completions; at least six runs active at once). The proposals differ in information hierarchy, navigation model, density, typographic voice and colour strategy; see `docs/proposals/live-mission-control/README.md` and the comparison page for screenshots and the decision table.

- **A. Operations Deck** (https://claude.ai/artifact/EYQV89TdyY9Qttw6hUcdS1): table-first, dense, sidebar navigation like today's Mission Control; for the operator who watches many agents at once.
- **B. Flight Map** (https://claude.ai/artifact/LmvTvcTjtgYPmpw7hG2mFb): the live agent map is the hero; top-bar navigation; inspector in a side drawer; for the superadmin cockpit and client demos.
- **C. Command Queue** (https://claude.ai/artifact/UtoCtk3c9nEiVD1SVPnTc7): human intervention first (needs you, running, done); calmer palette with one attention colour; for managers who mostly approve and instruct.
- Comparison page with screenshots and the decision table: https://claude.ai/artifact/WUfjz3Agff2HFmuGvyiNpY

## 5. Decision needed from the owner

Choose A, B or C, or a combination of named parts. After that: ADR for the transport (SSE over LISTEN/NOTIFY), the migration, and the build in slices (stream and fleet overview first, then inspector, map, control). No change to the running architecture before that approval.
