Status: **backend, agent nomination and acceptance tests delivered 2026-11-09; Mission Control UI in progress**. Spec section 4H.

## Scope

In: migration 0007 (`agency_knowledge_records`, `agency_knowledge_versions`, `agency_knowledge_transitions`, `knowledge_promotion_requests`, `knowledge_promotion_reviews`, `methodology_templates`, `template_adoptions`, `evaluation_cases`, `knowledge_deprecation_events`; `skill_release_channels` and `knowledge_access_logs` already existed); record lifecycle `draft -> in_review -> approved -> published -> deprecated -> archived` with reviewer and audit trail; Client -> Agency promotion gate (nomination by an agent, human review with rights, security and identifiability checks, publication as a self-contained record); Agency -> Client adoption of one pinned version per tenant with the tenant's own parameter values; release, rollback and deprecation without touching adoptions; agency full-text search over agency tables only; Mission Control module Agency Intelligence Vault (Knowledge Library, Skills Registry, Interview Library, Industry Blueprints, Design System, Tech Watch, Pending Knowledge Reviews, Version History, Templates and adoptions) and the `/agency` landing page.

## Design decisions (ADR-020)

- Agency tables carry no `tenant_id`. RLS allows them only in agency scope (`app_actor_scope() = 'agency'`); tenant scope sees nothing, the operator role sees metadata columns only (never `body_markdown`, `parameters` or `proposed_generic_statement`).
- Promotion requests are tenant rows (source tenant) that reviewers in agency scope may read and decide. Agents can only insert them in state `nominated`; every other transition is refused for agents by the trigger.
- Approval of a promotion needs a review row by a human with `rights_check`, `security_check` and `identifiability_check` all true and a `consent_status` of `granted` or `not_required`. Publication creates a new record (`origin = abstracted_from_client`) that carries the request id as agency-internal metadata but no tenant id, slug, source ids or actor identities of the tenant.
- No self-approval of own records (the author needs a second person) except for the superadmin, whose self-approval is recorded on the transition. Records published from an approved promotion are exempt because the review already happened on the request.
- Adoptions pin `record_version_id`; the pin cannot be changed in place (trigger). Releasing a new version, rolling the record back or deprecating it never changes an adoption; the impact count is logged in `knowledge_deprecation_events`. A tenant moves versions only through a new adoption (previous one `superseded`) or a rollback (previous one `rolled_back`, earlier version re-adopted as a new client revision).

## Acceptance (spec 4H, MVP criteria 1 to 6)

Covered by `packages/core/test/agency-knowledge.test.ts` against Postgres with RLS:

1. Admin creates, reviews and publishes a method template and adopts one version into two synthetic tenants (test 1).
2. An agent nominates a reusable insight; it is not published without a reviewer and a rights check (test 2, demo flow step 10).
3. The reusable method works in a second simulated industry with its own values and data sources (test 1: hotel tenant with PMS and a different accounting system).
4. Rights and search tests prove the agency vault returns no confidential client documents, facts or run traces from tenant A or B (test 4).
5. A published method can be replaced, rolled back or deprecated without uncontrolled changes to running client adoptions (test 5).
6. Mission Control shows which method versions are installed per client without the client's private content (test 6: operator role reads the adoption matrix, `parameters` and record bodies are refused).
